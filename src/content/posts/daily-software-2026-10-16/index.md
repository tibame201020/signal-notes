## 新增訊號｜檢查、修復與驗收分開
GitHub 10/15 公布拉取請求 AI Scan 正式推出，補充 CodeQL 靜態掃描的偵測面；同日代理式自動修復正式推出，可跨多個檔案分析並提出修補。兩者仍需人員審查、固定測試資料與部署驗證。[GitHub 10 月官方公告](https://github.blog/changelog/month/10-2026/)。公告頁未提供可核對的 05:00 前時分，故列為補刊日期層級觀察。
**推論：** 工程品質要分成「可重現的漏洞案例→偵測與誤報→修補差異→單元及整合測試→實際部署」，不應只統計模型成功生成程式碼的次數。**依據：** 官方功能定位。**為什麼這樣判斷：** 靜態掃描的通過不保證執行環境不存在回歸。

## 供應鏈控制與開源工具
10/14 GitHub 工作流程依賴鎖定檔公開預覽使版本標籤與實際提交識別可追溯；10/15 的代理修復則控制另一個面向：變更理由、測試、審批和產物。兩者互補，不能取代最小權限。[依賴鎖定公告](https://github.blog/changelog/2026-10-14-github-actions-workflow-lockfiles-in-public-preview/)。
## 資料結構與架構
記錄來源檔 SHA、掃描器版本、漏洞位置、修補後 SHA、測試輸入雜湊和部署回執，形成不可混淆的稽核鏈。若自動修補無法維持 API 契約，應失敗並回報，而不是以表面測試通過掩飾。
